# Service Mesh 缺点

## 1. 性能开销

```
请求延迟增加
┌─────────┐     ┌─────────┐     ┌─────────┐
│  App A  │────→│  Envoy  │────→│  App B  │
│         │ 0ms │ Sidecar │ 3ms │         │
└─────────┘     └─────────┘     └─────────┘

无 Sidecar:  0.5ms
有 Sidecar:  3-5ms  (增加 2-4ms)
```

| 开销来源 | 影响 | 数值 |
|---------|------|------|
| **网络跳转** | 本地回环 | +1-2ms |
| **TLS 加密** | CPU 消耗 | +1-2ms |
| **指标收集** | 内存/CPU | +5-10% |
| **Sidecar 内存** | 每个 Pod 额外 | +50-100MB |

## 2. 复杂度增加

```
问题排查更复杂
┌─────────────────────────────────────┐
│  User Request                       │
│     │                               │
│     ▼                               │
│  ┌─────────┐  是 Envoy 问题？       │
│  │  Envoy  │  是应用问题？           │
│  │ Sidecar │  是网络问题？           │
│  └────┬────┘                        │
│       │                             │
│  ┌────┴────┐                        │
│  │   App   │                        │
│  └─────────┘                        │
│                                     │
│  以前：curl 直接测试应用             │
│  现在：先看 Envoy 日志，再看应用日志  │
└─────────────────────────────────────┘
```

## 3. 学习成本

| 方面 | 以前 | 现在 |
|-----|------|------|
| **网络问题** | 看应用日志 | 先看 Envoy 配置，再看 xDS，再看应用日志 |
| **路由配置** | Nginx 配置 | VirtualService + DestinationRule + Gateway |
| **调试工具** | curl, tcpdump | istioctl, envoy-configdump |

## 4. 升级风险

```
Istio 升级 = 所有 Pod 重启
┌─────────┐    ┌─────────┐    ┌─────────┐
│ Pod 1   │    │ Pod 2   │    │ Pod 3   │
│ v1.18   │    │ v1.18   │    │ v1.18   │
└─────────┘    └─────────┘    └─────────┘
     │              │              │
     └──────────────┼──────────────┘
                    ▼
            滚动升级 Istio
                    │
     ┌──────────────┼──────────────┐
     ▼              ▼              ▼
┌─────────┐    ┌─────────┐    ┌─────────┐
│ Pod 1   │    │ Pod 2   │    │ Pod 3   │
│ v1.19   │    │ v1.19   │    │ v1.19   │
│ 重启    │    │ 重启    │    │ 重启    │
└─────────┘    └─────────┘    └─────────┘

风险：所有服务同时受影响
```

## 5. 不适合的场景

| 场景 | 原因 | 替代方案 |
|-----|------|---------|
| **单体应用** | 没有服务间调用 | Nginx Ingress |
| **低延迟要求** | 金融交易 < 1ms | 直连 + 硬件加速 |
| **资源受限** | IoT/边缘设备 | Linkerd (更轻量) |
| **小团队** | 运维人力不足 | 云厂商托管方案 |

## 6. 具体数据

| 指标 | 无 Service Mesh | Istio | Linkerd |
|-----|----------------|-------|---------|
| **延迟增加** | 0ms | 3-5ms | 1-2ms |
| **内存/Pod** | 0MB | 100MB | 20MB |
| **CPU 增加** | 0% | 10-15% | 5% |
| **控制平面** | 无 | 3 个组件 | 2 个组件 |

## 7. 面试回答

> "Service Mesh 的主要缺点是性能开销和复杂度。每个请求经过 Sidecar 增加 3-5ms 延迟，每个 Pod 额外消耗 100MB 内存。问题排查也更复杂，需要理解 Envoy 配置。适合中大型微服务架构，小团队或低延迟场景不建议使用。"

## 8. 什么时候不用

```
┌─────────────────────────────────────┐
│  服务数量 < 5                       │
│  团队规模 < 10人                    │
│  延迟要求 < 10ms                    │
│  没有多语言服务                     │
│                                     │
│  → 不用 Service Mesh                │
│  → 用 Nginx Ingress + 代码库即可    │
└─────────────────────────────────────┘
```
